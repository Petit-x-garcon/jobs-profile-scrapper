# Internationalization (next-intl)

- The app supports exactly two languages: Khmer (`km`) and English (`en`). Both are required: every screen and message must work in both. Don't add other locales.
- Which one is the **default** is a per-project setting. It is named in the "Stack and conventions" section of `AGENTS.md` and set in one place in code: `DEFAULT_LOCALE` in `apps/web/i18n/routing.ts`. Don't hard-code `"km"` or `"en"` as the default anywhere else; read it from that constant. To switch a project's default, change those two places only.
- Messages live in `apps/web/messages/km.json` and `apps/web/messages/en.json`; configuration is in `apps/web/i18n/`.
- Every user-facing string goes through a translation, including button labels, placeholders, `aria-label`s, toast messages, validation messages and error fallbacks. No hard-coded text in components.
- In client components use `const t = useTranslations("<namespace>")`; in server components use `getTranslations`.
- Add each new key to **both** files in the same change, with the same nesting. Namespaces follow the feature (`common`, `users`, …); put shared words (Save, Cancel, Delete) in `common`.
- Write the default locale's text first, then translate. If you can't write a proper translation (usually Khmer), put the default locale's text in the other file and say so in your summary so someone can translate it. Never leave a key missing from one file.
- Use ICU placeholders for variable parts (`"deleted": "Deleted {name}"`), never string concatenation, because word order differs between Khmer and English.
- Format dates and sizes with `formatDate(iso, locale)` and `formatBytes(bytes)` from `lib/format.ts`, so they follow the active locale.
- Fonts: Noto Sans Khmer via `next/font/google` (khmer + latin subsets), whichever locale is the default. Khmer script needs generous line height, so don't tighten `leading-*` on body text.
- Check every UI change in both `km` and `en`, since Khmer text is often longer and wraps differently.
